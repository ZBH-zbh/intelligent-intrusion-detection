# 答辩结果摘要

更新时间：2026-09-14

## 一句话方案

PYNQ-Z2 的 PL 端用 4 个 HLS 流水 IP 完成灰度、帧差、阈值和形态学处理，PS 端完成轮廓、合框、报警与显示；同时提供相同业务规则的 OpenCV 纯软件版作为对照。

## 本次新增工作

1. 把队长工程的实际地址、RGB32 输入和低 8 位掩码接口固定为唯一基线。
2. 建立 OpenCV 纯软件检测、公共后处理及可复现的一致性指标。
3. 优化 HLS 中运行时尺寸乘法，保持 II=1，并用 CSim 覆盖灰度、阈值、连续帧、腐蚀边界和 TLAST。
4. 改进 PS 端 RGB32 打包、DMA 超时/错误诊断、缓存同步和资源释放。
5. 生成独立优化 IP 仓库、Vivado 工程及 bit/hwh，不覆盖队长基线。
6. 用非对称 DMA 缓冲、双向 `mixChannels` 和 100 us 低 CPU 轮询消除 PS↔PL 数据整理瓶颈。

## 可量化结果

- HLS 估算总 DSP：14→2。
- Vivado 系统级 DSP：16→3，减少 81.25%。
- LUT：3956→3725，减少 5.84%。
- 寄存器：5143→4695，减少 8.71%。
- BRAM：27→27。
- 优化实现 WNS：+0.225 ns，WHS：+0.031 ns，满足 100 MHz。
- 本地合成帧一致性：像素 99.9975%，掩码 IoU 99.8298%，目标数/bbox/报警均 100%。
- Python 自动测试：12/12 通过。
- PYNQ 正式无显示测试：OpenCV 48.40 FPS，优化 PL 50.18 FPS，PL 加速 1.04×（+3.67%）。
- 单核 CPU：OpenCV 99.98%，优化 PL 96.25%，降低 3.73 个百分点。
- PS I/O 优化使同一优化 PL 从 20.25 FPS 提升到 50.18 FPS，提升 2.48×。
- 优化版约 3 分钟持续回归稳定，实时画面、目标框、报警、G1 蜂鸣器和资源释放全部通过；Jupyter 显示 17.1±0.1 FPS。

## 必须如实说明的边界

Windows 的 7779.55 FPS 是 OpenCV 本地 CPU 参考，2666.68 FPS 是 HLS 整数公式的 CPU 模拟，两者都不是 FPGA 性能。正式结论只采用 PYNQ-Z2 上的 48.40/50.18 FPS。实时 Jupyter 的约 17 FPS 包含摄像头、JPEG 和网页刷新，也不能代替无显示核心吞吐。PL 的 1.04× 加速真实但幅度有限，不应夸大。

## 常见答辩问题

**为什么不用 PL 输出 bbox？**  
实际可运行基线就是 PL 输出二值掩码、PS 做轮廓和报警。本项目优先保证与队长成品兼容，而不是重新设计高风险接口。

**为什么 OpenCV 与 PL 不会逐像素绝对相同？**  
OpenCV 标准灰度有自己的舍入方式，HLS 使用整数权重近似；阈值附近可能相差极少像素，因此同时报告像素一致率、掩码 IoU 和业务层 bbox/报警一致率。

**主要优化来自哪里？**  
PL 资源优化来自消除 HLS 中不必要的运行时 `width * height` 乘法器；端到端性能优化主要来自非对称 DMA 缓冲和 OpenCV `mixChannels`，避免 CPU 在非缓存 CMA 上进行多轮数组扫描。接口和处理语义均保持不变。

**如何保证数据公平？**  
正式 runner 先把同一帧集载入内存，排除采集和显示时间；两端使用相同预热、轮次和 PS 后处理，并保存原始 CSV/JSON、环境版本和 bitstream 哈希。

**为什么 PL 加速只有约 1.04×？**  
当前双方都在 PS 执行 7×7 闭运算、3×3 开运算、轮廓和报警；分阶段实测仅 PS 形态学就约 12.17 ms/帧，是最终总耗时的约 62%。若追求更大加速，需要把这部分继续迁移到 PL，而不是夸大现有数据。
