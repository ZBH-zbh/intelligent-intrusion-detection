# PYNQ-Z2 智能入侵检测系统优化建议清单

更新时间：2026-09-14  
状态：推荐组合、R09-A、R10、R11 及板端 PS I/O 优化均已执行并验证；原始工程未覆盖。

## 1. 评审基线

实际数据流为：

```text
PS 摄像头/BGR
  -> RGB32 打包
  -> AXI DMA MM2S
  -> rgb2gray
  -> frame_diff
  -> threshold
  -> morphology（实际为 3×3 腐蚀）
  -> AXI DMA S2MM
  -> PS 二次形态学、轮廓、合框、报警和显示
```

### 1.1 已实现结果

| 项目 | 当前结果 |
|---|---|
| 器件 | xc7z020clg400-1 |
| PL 时钟 | 100 MHz |
| 实现后 WNS/WHS | +0.611 ns / +0.031 ns，时序通过 |
| 布线 | fully routed，routing errors = 0 |
| LUT | 3956 / 53200，7.44% |
| 寄存器 | 5143 / 106400，4.83% |
| BRAM Tile | 27 / 140，19.29% |
| DSP | 16 / 220，7.27% |
| HLS 像素循环 | 4 个模块均达到 II=1 |

在 100 MHz、II=1 的理想连续流条件下，320×240 一帧只包含 76800 个像素，PL 像素流水线的理论处理时间约 0.768 ms。该值不包含 DMA、PS 打包、缓存同步、后处理和显示，因此当前端到端瓶颈更可能位于 PS/DMA/显示链路，需要实测确认。

### 1.2 当前 HLS 资源估计

| IP | BRAM_18K | DSP | FF | LUT | 估计关键延迟 | 循环 II |
|---|---:|---:|---:|---:|---:|---:|
| rgb2gray | 0 | 5 | 509 | 465 | 6.912 ns | 1 |
| frame_diff | 64 | 3 | 409 | 417 | 6.912 ns | 1 |
| threshold | 0 | 3 | 486 | 472 | 6.912 ns | 1 |
| morphology | 2 | 3 | 958 | 936 | 7.031 ns | 1 |

4 个 IP 中各有一个由 `width * height` 推导出的 32 位乘法器，每个估计使用 3 个 DSP，共 12 个 DSP。Vivado 的部分 DRC Warning 也来自这些乘法器未充分流水化。

## 2. 建议采用的优化组合

建议先批准 R01～R08。它们能建立可靠对比基线、修复明显可靠性问题，并为后续 PL 改动提供可验证证据。

R09 涉及算法语义和重新生成 bitstream，建议先完成基线对比，再从三个方案中选择一个。

### 2.1 推荐执行

| 编号 | 优化项 | 改动范围 | 预期收益 | 风险/代价 | 需要 bitstream |
|---|---|---|---|---|---|
| R01 | 建立同输入、同参数的统一对比基准 | 新增 Python 对比工具 | FPS、CPU、效果数据可复现 | 需要后续在 PYNQ 采集固定帧集 | 否 |
| R02 | 软件版与 PL 版共用轮廓、合框、报警后处理 | Python | 排除后处理差异，便于解释比赛结果 | 需保持现有行为兼容 | 否 |
| R03 | 修复 DMA 无限忙等 | Python MMIO 驱动 | DMA 错误或卡死时能超时并报告状态 | 超时阈值需上板确认 | 否 |
| R04 | 修复 overlay 重复下载和异常清理 | Python | 缩短启动；确保异常时关闭蜂鸣器、释放摄像头和缓冲区 | 低 | 否 |
| R05 | 重做计时与 CPU 统计 | Python | 输出平均值、P50/P95、进程 CPU、系统 CPU | 基准模式与演示模式需分开 | 否 |
| R06 | 优化 BGR 到 `0x00RRGGBB` 打包并复用临时数组 | Python/NumPy | 减少每帧颜色转换和内存分配 | 必须逐像素验证格式 | 否 |
| R07 | 基准模式关闭显示；演示模式降低 JPEG/UI 刷新频率 | Python/Jupyter | 防止浏览器显示吞吐掩盖 PL 性能 | 显示帧率与处理帧率需分别标注 | 否 |
| R08 | 增加 HLS C 测试平台和软件参考模型 | HLS 测试代码 | 覆盖灰度、帧差、阈值、腐蚀、TLAST 和边界 | 需要配置 Vitis HLS 命令环境 | 否 |

### 2.2 推荐但必须重新生成 bitstream

| 编号 | 优化项 | 依据 | 预期收益 | 风险 |
|---|---|---|---|---|
| R09 | 修正 morphology 的实现与文档不一致 | 当前代码只执行 3×3 腐蚀，且输出相对中心锚点右下偏移约 1 像素 | 检测效果更可解释，可减少或移除 PS 二次形态学 | 会改变掩码和检测结果；必须先仿真、再生成新 bitstream、最后上板回归 |
| R10 | 消除 4 个 `width * height` 运行时乘法器 | HLS 报告显示每个模块因此使用 3 个 DSP | 理论可减少约 12 个 HLS DSP，并消除对应 DRC 流水化警告 | 对端到端 FPS提升可能很小；必须保持 320×240 和接口兼容 |
| R11 | 增加输入参数边界保护或固定为 320×240 | frame_diff 最大缓冲为 76800，morphology 行缓冲最大宽度为 320 | 防止错误参数导致越界和不可预测输出 | 固定参数会降低接口灵活性，但符合当前项目约束 |

R09 的三种候选方案：

1. **R09-A，最小风险**：保留当前 3×3 腐蚀，修正文档和软件参考模型，使比较严格等价。
2. **R09-B，推荐优化方向**：实现严格定义、中心锚点和明确边界规则的 3×3 开运算，再根据实测决定是否保留 PS 的 7×7 闭运算。
3. **R09-C，最高工作量**：把当前 PS 的 7×7 闭运算 + 3×3 开运算完整迁移到 PL，目标是显著降低 PS CPU，但需要多级行缓冲和更多验证。

推荐先以 R09-A 建立基线，随后尝试 R09-B。只有 R09-B 后 PS CPU 仍明显受形态学限制时，才考虑 R09-C。

### 2.3 可选实验，不默认写入正式版本

| 编号 | 实验项 | 用途 | 采用条件 | 需要 bitstream |
|---|---|---|---|---|
| E01 | 4 个 HLS IP 设置 `auto_restart` | 减少每帧 4 次 AXI-Lite 启动写操作 | 板端验证连续多帧无错帧、无死锁且确有收益 | 否 |
| E02 | DMA 轮询中加入让步或短等待 | 降低 ARM 忙等 CPU | CPU 明显下降且 FPS 下降可接受 | 否 |
| E03 | OpenCV 默认线程与单线程各测一轮 | 解释软件版 CPU/FPS关系 | 报告中明确线程数，不挑选性呈现结果 | 否 |
| E04 | 记录处理阶段分项耗时 | 定位打包、DMA、PS 后处理、JPEG 各自瓶颈 | 计时代码开销足够小 | 否 |

### 2.4 暂缓或不建议

| 编号 | 方向 | 判断 | 原因 |
|---|---|---|---|
| D01 | 合并 4 个 IP 为单个 HLS dataflow IP | 暂缓 | 当前跨 IP 已是 AXI-Stream 串接且 II=1；先证明 AXI-Lite 启动开销值得承担重构风险 |
| D02 | 提高 PL 时钟到 110/125 MHz | 不建议首轮做 | 100 MHz 下 WNS 仅 0.611 ns，且端到端更可能受 PS/DMA/显示限制 |
| D03 | 在 PL 实现连通域和 bbox | 暂缓 | 工程复杂度高，偏离当前已跑通的方案 A，未证明是当前瓶颈 |
| D04 | 修改到更高分辨率 | 不执行 | 用户明确要求保持 320×240；修改必须重新生成 bitstream 并另行确认 |
| D05 | 强行使用 PYNQ `ip_dict` | 不执行 | MMIO 已稳定绕过 hwh 解析风险，切换没有直接收益 |
| D06 | 把 PL 输出流改成 8 bit | 暂缓 | 会联动 DMA 数据宽度、打包和软件接口，收益需先由带宽数据证明 |

## 3. 工程可复现性修复

以下问题建议纳入工程优化，但不改变算法：

| 编号 | 问题 | 处理建议 |
|---|---|---|
| P01 | 工程位于 `D:\FPGA2.0\pl\pl`，多嵌套一层 | 暂不移动原工程；在复现文档写明真实路径，避免破坏 `.xpr` 相对引用 |
| P02 | HLS `.project` 含队长电脑 `C:\Users\ZBH\...` 绝对路径 | 新增以当前工作区相对路径运行的 Tcl 构建入口，不依赖 Eclipse 工程元数据 |
| P03 | 顶层 `hls\rgb2gray.cpp` 为 0 字节 | 确定单一权威源码；修复前不删除任何副本 |
| P04 | 根目录 hwh 名为 `design_1_wrapper .hwh` | 保留原件，生成正确命名的 `design_1_wrapper.hwh` 副本，并再次校验哈希 |
| P05 | 缺少自动化 HLS 测试 | 为 4 个 IP 增加最小 C 仿真测试，不追求无关文档或复杂测试框架 |
| P06 | Vivado/Vitis HLS 当前终端不在 PATH | 用户提供安装目录或使用 Xilinx Command Prompt 后，再执行只读版本检查 |

## 4. 对比指标与建议验收线

| 指标 | 统计方法 | 初步验收线 |
|---|---|---|
| 核心 FPS | 同一批内存帧，预热后 200 帧 × 3 轮 | 报告平均、标准差、P50/P95 |
| 端到端 FPS | 摄像头采集 + 处理；显示模式单独统计 | PL 版不低于当前稳定水平且无明显卡顿 |
| CPU | Python 进程 CPU 与系统 CPU，固定采样周期 | PL 版应低于纯软件版；如不是，给出分项瓶颈解释 |
| 掩码一致率 | 相同输入逐像素比较 | >= 95% |
| 掩码 IoU | 前景交并比 | >= 0.85；空掩码单独处理 |
| 目标数一致率 | 每帧目标数相同的比例 | >= 90% |
| bbox IoU | 一对一匹配后的平均 IoU | >= 0.70 |
| 报警一致率 | 每帧报警布尔值比较 | >= 95% |

如果选择重做 morphology，优化前版本先作为基线保留；优化后既要与软件参考比较，也要报告检测效果变化，不能只报告 FPS。

## 5. 最终执行结果

- [x] R01～R08：已完成统一基准、公共后处理、DMA 可靠性、统计、数据打包、显示拆分和 HLS 测试。
- [x] R10～R11：已消除 4 个运行时尺寸乘法器并固定 320×240 边界；HLS 估算 DSP 14→2，系统级 DSP 16→3。
- [x] R09-A：保留队长当前 morphology 语义，并让软件参考与其严格对应；未执行会改变检测语义的 R09-B。
- [x] E02、E04：已合入 100 us DMA 轮询让步并完成分阶段耗时诊断。
- [x] E03：正式 OpenCV 对比固定为单线程，避免线程数变化干扰结果。
- [ ] E01：未启用 `auto_restart`；实测每帧启动 4 个 IP 仅约 0.14 ms，当前收益不足以抵消连续运行风险。
- [ ] R09-C：未把 PS 形态学整体迁移到 PL；它是下一轮提升加速比的首选方向，但会改变硬件结构，需重新确认、仿真和生成 bitstream。
- [x] D01～D03、D06 保持暂缓，D04～D05 未执行，符合原决策。
